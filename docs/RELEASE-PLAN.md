# Закрытые полные загрузки по ОС

Статус: **подтверждённый вариант доставки, ещё не включён и не опубликован**. Исходники остаются в компактной ветке `main`. Для Windows x64, macOS ARM64 и Linux x86_64/aarch64 готовятся отдельные distribution-версии с полными проверенными файлами.

## Почему обычного Release asset недостаточно

Один asset GitHub Release должен быть меньше 2 GiB. Уже сжатый Tails в существующем общем архиве занимает 1 868 528 315 bytes; три Android APK добавляют примерно 332 MB без остальных компонентов. Полный комплект не объявляется укладывающимся в лимит и не теряет функции ради размера. Ограничение — [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).

## GitHub archive с настоящими LFS-файлами

GitHub поддерживает включение содержимого LFS в ZIP/tar-архивы репозитория. Для этого нужны закоммиченные tracking rules в `.gitattributes` и настройка **Include Git LFS objects in archives**. По умолчанию в архив попадают указатели. Внешний LFS server этим механизмом не покрывается. [Официальная документация](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/managing-git-lfs-objects-in-archives-of-your-repository).

План: для каждой ОС зафиксировать отдельный distribution commit с готовой программой, обязательными соседними ресурсами, полным offline Data и лицензиями. Бинарники хранятся отдельными LFS-объектами; общий ZIP генерирует GitHub. Кнопка README ведёт на архив **проверенного commit**, доступный владельцу через обычный авторизованный браузер GitHub. Токены не встраиваются в ссылку или программу. После извлечения пользователь открывает готовое приложение; Git, LFS, Python и сборка ему не нужны.

Для Free/Pro официальный предел одного LFS-файла — 2 GB. Все 42 code-pinned Data-файла меньше даже строгой границы 2 000 000 000 bytes; самый большой Tails IMG — 1 889 533 952 bytes. Готовый ZIP не загружается в LFS как один большой объект. [Пределы LFS и формат указателя](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-git-large-file-storage).

Одинаковые bytes в разных distribution-версиях имеют один SHA-256 OID. При оценке считаем уникальные объекты; протокол LFS не требует повторной передачи уже имеющегося OID. Это позволяет повторно использовать Tails и другие общие компоненты между ОС. [Спецификация Git LFS Batch API](https://raw.githubusercontent.com/git-lfs/git-lfs/main/docs/api/batch.md).

## Квоты и расходы — отдельный gate

Free/Pro включают 10 GiB storage и 10 GiB download bandwidth. Скачивание архивов с LFS расходует bandwidth владельца; новые версии изменённых файлов добавляют весь объект к storage. Бюджет $0 блокирует превышение, удалённый бюджет не ограничивает расходы. [Правила биллинга LFS](https://docs.github.com/en/billing/concepts/product-billing/git-lfs).

Текущий тариф, уже использованная квота и бюджет **не подтверждены**. Read-only API usage и summary вернули HTTP 404 с требованием scope `user`; разрешения авторизации не расширялись. Неизвестное значение не принимается за ноль. LFS upload, изменение настроек archive/billing/budget и платный CI не выполнялись.

Публичный Data-каталог содержит 42 пути, 41 уникальный SHA-256 объект, **3 113 712 627 bytes** уникальных данных. Это только нижняя часть набора: к ней добавятся уникальные файлы окончательных native-сборок. До загрузки нужен полный frozen inventory, текущая доступная квота и явное решение владельца о допустимых расходах. Одна проверочная загрузка каждого большого OS-архива тоже расходует bandwidth; бесплатность четырёх таких проверок не предполагается.

## Условия включения кнопок

1. Проверены frozen UI/backend, исходники и весь релизный состав; пользовательские данные и raw proofs исключены.
2. Полные native-комплекты сохраняют Tails, Android и остальные заявленные сценарии. Измерены каждый файл, уникальные OID и общий объём с запасом на новую версию.
3. Подтверждены квоты и бюджет либо получено конкретное разрешение владельца на расходы. Источник разрешения фиксируется до upload; молчание не считается согласием.
4. Приватность репозитория проверена непосредственно перед source push, distribution push и загрузкой объектов. Включение LFS в архив отдельно подтверждено; создание public-доступа не допускается.
5. Для каждой ОС извлечён именно GitHub-архив distribution commit. Проверены реальные файлы вместо LFS pointers, manifest/hash и подписи издателей, executable bits, symlinks и подпись `.app`, отсутствие персональных данных, запуск и все обязательные соседние пути.
6. Проверены авторизованный доступ, отказ без доступа, полнота offline-сценария и понятная инструкция. Только затем кнопки получают действующие ссылки.

GitHub может заново сгенерировать ZIP с другим сжатием. Поэтому фиксируются commit и хеши **извлечённых файлов**, а постоянный SHA-256 внешнего автоматически создаваемого ZIP не обещается. GitHub отдельно рекомендует Release assets, когда требуется стабильность внешнего архива для security-сценария; здесь это ограничение учитывается проверками содержимого и подписей. [Гарантии архивов](https://docs.github.com/en/repositories/working-with-files/using-files/downloading-source-code-archives).

Проверка схемы на документации не равна готовому артефакту. До успешной полной проверки большие архивы могут потребовать дополнительного времени или повторной загрузки. Альтернативный multipart-загрузчик рассматривается только если этот путь не проходит испытания; ручная сборка для пользователя не является запасным решением. Независимый source push в private `main` не зависит от одобрения затрат LFS.
