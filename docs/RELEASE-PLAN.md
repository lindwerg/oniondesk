В проверявшихся архивах присутствовали настоящие LFS-файлы. Все полностью полученные файлы до места обрыва прошли проверку, но полный Mac-комплект не удалось получить:

Отдельный LFS-объект Tails размером 1 889 533 952 bytes удалось прочитать целиком; проверка завершилась успешно. Этот результат подтверждает отдельный объект, но не полноту GitHub ZIP/tar и не причину обрыва. Полная доставка архивов остальных ОС также не объявляется подтверждённой.

Начат отдельный причинный эксперимент с четырьмя частями под статусом **`NOT_RUNNABLE_DO_NOT_LAUNCH`**. Это технический материал, который нельзя запускать или выдавать за пользовательский комплект. Продуктовый загрузчик для него ещё не создан; ссылки на эксперимент не используются в пользовательских загрузках.

## Почему одного Release asset недостаточно

Один asset GitHub Release должен быть меньше 2 GiB. Уже сжатый Tails в существующем общем архиве занимает 1 868 528 315 bytes; три Android APK добавляют примерно 332 MB без остальных компонентов. Полный комплект не объявляется укладывающимся в лимит и не теряет функции ради размера. [Ограничение GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).

GitHub поддерживает включение LFS-содержимого в ZIP/tar-архивы при наличии tracking rules в `.gitattributes` и настройки **Include Git LFS objects in archives**. По умолчанию в архив попадают указатели; внешний LFS server этим механизмом не покрывается. Это поддерживаемая возможность, но успешная полная доставка данного комплекта всё равно требует фактической проверки. [Git LFS в архивах](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/managing-git-lfs-objects-in-archives-of-your-repository).

Для Free/Pro официальный предел одного LFS-файла — 2 GB. Все 43 runtime Data-файла меньше даже строгой границы 2 000 000 000 bytes. Готовый большой ZIP не хранится в LFS как единый объект. [Пределы LFS и формат указателя](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-git-large-file-storage).

Одинаковые bytes в distribution-версиях имеют один SHA-256 OID. При оценке считаются уникальные объекты; LFS не требует повторной передачи уже имеющегося OID. Это позволяет переиспользовать Tails и другие общие компоненты между ОС. [Git LFS Batch API](https://raw.githubusercontent.com/git-lfs/git-lfs/main/docs/api/batch.md).

## Квоты и расходы

Free/Pro включают **10 GiB storage** и **10 GiB download bandwidth в месяц**. Скачивание архивов с LFS расходует bandwidth владельца; новая версия изменённого файла добавляет к storage весь объект. Проверочные загрузки также расходуют bandwidth. [Правила биллинга LFS](https://docs.github.com/en/billing/concepts/product-billing/git-lfs).

Бюджет платного перерасхода оставлен **$0**; настройки фактического биллинга не менялись. Бюджет $0 блокирует платное превышение, а удалённый бюджет не ограничивает расходы. Экран usage обновляется с задержкой: показанное там значение не доказывает нулевой расход после upload и проверочных скачиваний. Оставшуюся квоту нельзя считать равной 10 GiB без актуальных данных.

## Условия включения прямых загрузок

1. Проверены frozen UI/backend, исходники и весь релизный состав; пользовательские данные и raw proofs исключены.
2. Полные native-комплекты сохраняют Tails, Android и остальные заявленные сценарии. Измерены каждый файл, уникальные OID и общий объём с запасом на новую версию.
3. Подтверждены доступные квоты и бюджет. Платное превышение не включается без конкретного разрешения владельца; молчание не считается согласием.
4. Приватность репозитория проверена непосредственно перед source push, distribution push и загрузкой объектов. При использовании GitHub archive отдельно подтверждено включение LFS; public-доступ не создаётся.
5. Для каждой ОС полностью получен именно публикуемый комплект. Для GitHub archive извлечён архив зафиксированного distribution commit. Проверены реальные файлы вместо LFS pointers, manifest/hash и подписи издателей, executable bits, symlinks и подпись `.app`, отсутствие персональных данных, запуск и все обязательные соседние пути. Альтернативный способ доставки должен пройти те же проверки целого комплекта.
6. Проверены авторизованный доступ, отказ без доступа, полнота offline-сценария и понятная инструкция. Только затем карточки получают действующие ссылки на загрузки.

GitHub может заново сгенерировать ZIP с другим сжатием. Поэтому фиксируются commit и хеши **извлечённых файлов**, а постоянный SHA-256 внешнего автоматически создаваемого ZIP не обещается. GitHub рекомендует Release assets, когда требуется стабильность внешнего архива для security-сценария; здесь учитываются лимит размера и проверки содержимого. [Гарантии архивов](https://docs.github.com/en/repositories/working-with-files/using-files/downloading-source-code-archives).

Mac-комплект предназначен для Apple Silicon с macOS 15+, имеет подпись ad-hoc без Apple notarization и Developer ID. Готового Mac Intel нет. На Linux ARM64 отсутствует проверенный стабильный официальный маршрут Tor Browser. Технический эксперимент не меняет эти ограничения и не заменяет проверку на целевых системах.
