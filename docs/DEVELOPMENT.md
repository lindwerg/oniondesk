# Разработка и воспроизведение

Эта страница только для разработчиков. Пользователь получает готовый пакет и не выполняет эти команды. Репозиторий содержит исходники и тесты; реальные пользовательские данные, большие образы и исполняемые vendor-архивы исключены.

## Локальные unit-тесты

Из корня чистого checkout на Python 3.12:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r client/requirements.txt
.venv/bin/python -B -m unittest discover -s tests/docker/unit -v
```

Зависимости клиента закреплены в `client/requirements.txt`. Часть тестов платформенная и пропускается на другой ОС; часть требует системных инструментов Debian. Пропуски и ошибки сохраняются в результате, а не переименовываются в PASS.

Полный базовый стенд Debian 13 с system-пакетами, ShellCheck, Nginx и Chromium:

```sh
bash tests/docker/run.sh "$PWD/.build/test-logs"
```

Скрипт собирает локальный Docker image. Он не запускает платный GitHub runner. Исходники монтируются read-only; host-устройства, Docker socket и published ports контейнеру не передаются. Требуются локальный Docker и место для зависимостей. Сначала изучите [описание стенда](../tests/docker/README.md) и сценарии; гостевые образы проверяются отдельно и требуют значительно больше места.

## Что воспроизводимо, а что ещё требует работы

Unit-тесты используют временные каталоги, искусственные файлы и контролируемые ключи/пароли. Это позволяет проверять отказ при подмене и защитные контракты без live-кошелька и production-сервера. Браузерный smoke подменяет внешние backend, поэтому он не подтверждает работоспособность платного сервера, реальный USB или SMS.

Сборщики Python определяют корень относительно файла. Экспортированные `client/build-linux.sh` и Dockerfile также используют корень checkout; рабочие файлы сборки по умолчанию находятся в соседнем `<checkout>-build/linux/<architecture>`, отдельном от исходников. Пути с пробелами проверены mock-Docker regression-тестами. Историческая структура `outputs/remote-desktop-kit` не нужна для Linux-сборки из этого дерева.

Большой public Data-комплект восстанавливается из закреплённых каталогов. Сначала можно прочитать план без сети и записи:

```sh
.venv/bin/python -B tools/prepare-data.py
```

Для разработчика с уже подключённым Tor Browser и достаточным местом:

```sh
.venv/bin/python -B tools/prepare-data.py --fetch --socks-port 9150 --destination "$PWD/OnionDesk-Data"
```

Команда получает только 42 публичных файла, закреплённых кодом: проверяет точный размер, SHA-256 и официальные подписи Tails/Tor/Monero/Feather. HTTPS идёт через loopback `socks5h`, без прямого DNS и подхвата proxy/учётных данных окружения. Payload не исполняется и не извлекается. Повреждённый уже существующий файл останавливает подготовку; чужая непустая папка отклоняется. Точный служебный маркер сохраняется после прерванной подготовки для безопасного продолжения и удаляется только после полной успешной проверки. Готовый Data не содержит маркера и проходит строгий состав Windows packager. Повторный fetch готового немаркированного дерева выполняет полную read-only проверку состава/подписей и не создаёт сетевой сеанс. Объём и URL видны в плане до загрузки. Снимки публичных подписей, ключей, лицензий и двух Android text/provenance документов находятся в `release-metadata`, потому что эти точные исторические bytes не всегда воспроизводятся через изменяемую страницу издателя. JSON рядом с ними информационный; доверие задают каталоги кода.

Проверка существующего комплекта без записи:

```sh
.venv/bin/python -B tools/prepare-data.py --verify-only --destination "$PWD/OnionDesk-Data"
```

Read-only проверка имеющегося закреплённого комплекта выполнена: 42 файла и подписи издателей прошли; ни один payload не исполнялся. Сетевое восстановление всех больших файлов заново не выполнялось. Отказы downloader и транспорт через SOCKS проверены синтетическими тестами; доступность архивных URL остаётся внешним условием. `screenshots/real` содержит только 26 точечно просмотренных PNG из точного [списка](GUIDE-IMAGE-MANIFEST.json); raw JSON и пользовательские журналы туда не копировались. Это позволяет сохранять исходные native resource-контракты без импорта всей рабочей папки. Полный native build и настоящий запуск целевых ОС ещё не заявлены.

## Нативные сборщики

| Цель | Сборщик / зависимость | Текущее условие |
|---|---|---|
| macOS ARM64 | `client/build-native.py`, PyInstaller/pywebview, проверяющий GnuPG | macOS Apple Silicon; текущий stage GnuPG ожидает Homebrew Cellar ARM64. Ad-hoc подпись не заменяет notarization. |
| Windows x64 | `client/build-windows.py`, Windows Python/PyInstaller; `build-windows-setup.sh` и NSIS | Wine подходит для упаковки и ограниченного smoke; настоящий Windows проверяется отдельно. |
| Linux x86_64/aarch64 | `client/build-linux.sh`, Dockerfile, закреплённые build requirements | Checkout и отдельный buildwork; проверка каждой архитектуры и отдельный runtime smoke. |

Детали сборщиков с примерами от checkout: [Mac](../client/BUILD-NATIVE.md), [Windows](../client/BUILD-WINDOWS.md), [Linux](../client/BUILD-LINUX.md). Готовые пакеты и их проверка — условия [следующего релиза](RELEASE-PLAN.md).

## Проверенные vendor-ресурсы

Каталоги `offline_catalog.py`, `wallet_catalog.py`, `phone_catalog.py`, `feather_catalog.py` и `usb_tails.py` задают допустимые издательские источники, размеры/хеши и ключи проверки. Они не должны читать произвольный URL/хеш из release manifest для расширения доверия. Наличие файла в `OnionDesk-Data` не заменяет проверки официальной подписи и закреплённого каталога.

Релизная процедура должна получить перечисленные оригинальные ресурсы, проверить их, собрать полные per-OS payloads, сохранить исходные лицензии и только после этого подготовить пользовательские кнопки. В Git не добавляются скачанные APK/EXE/архивы, Tails IMG, Whonix-диски, seed, ADB state, SSH/GPG private homes, кеши и журналы.
